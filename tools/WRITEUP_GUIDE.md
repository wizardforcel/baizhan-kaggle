# writeup 写作手册（子代理用）

## 目标
为 `work/text/<slug>/` 里抽取出的比赛材料写一篇中文 writeup，保存到 `docs/<slug>.md`。
**样板**：`docs/20-newsgroups-ciphertext-challenge.md`（动手前先读一遍，风格、结构、代码注释方式都以它为准）。

## 读者
面向**编程和深度学习入门者**。不要假设读者懂术语；第一次出现的概念用一句大白话解释。

## 结构（必须完全一致）
```
# <比赛名>
## 一、比赛简介
### 1.1 比赛背景      # 这个比赛在做什么、数据从哪来、有什么难点
### 1.2 比赛目标      # 输入什么、输出什么、数据有哪些列
### 1.3 评价标准      # 用什么指标、怎么算、越高还是越低越好
## 二、解题过程
### 2.1 数据探索（EDA）
### 2.2 数据清洗
### 2.3 模型训练与超参数调优
### 2.4 模型测试与指标报告
## 三、总结
```
每个小节都是「一段代码 + 一段文字说明」交替。代码必须带**中文注释**，注释解释「为什么这么写」，不只是「这行在干嘛」。

## 叙述人称
解题过程用第一人称复数：**我们首先……，其次……，接着……，然后……，最后……**。
禁止「上述代码做了……」这种第三人称旁白。

## 内容来源
- 只依据 `work/text/<slug>/` 里的文本，不得编造分数、模型、库名。
- 优先选信息密度高的页面：`_index.txt` 里标题像「solution」「baseline」「tutorial」「EDA」「0.xx LB」的。
- 一般读 3～6 个页面即可，每个文件用 `Read` 的 `limit` 参数只读前 200～300 行，必要时用 `Grep` 定位关键代码，不要整篇硬读几 MB 的文件。
- 材料里如果有多份互相矛盾的方案，选**效果最好、讲得最清楚**的一条主线来写，其他方案在总结里一句话带过。
- 比赛背景如果材料里没写清楚（比如数据来源、指标定义），可以基于文件名和代码里的证据做最小合理推断；**推断不出就写得保守些**，不要瞎编具体数字。

## 代码要求
- 从材料里**提炼**代码，而不是整段照抄；去掉无关注释、调试输出、报错 traceback。
- 变量名保持材料里的写法，方便读者对照。
- 每段代码 10～40 行，注释用 `#`，中文。
- 如果材料里没有完整代码（比如只有讨论帖），就写「伪代码 + 文字说明」，并明确说这是根据讨论整理的思路。

## 篇幅
正文 2500～4500 个汉字。宁可写透一个方案，也不要罗列五个方案。

## 质量检查（交稿前自查）
1. 三大部分、四个小节齐全，标题层级和样板一致。
2. 有 6 段以上带中文注释的代码。
3. 全篇第一人称，没有「上述」「该代码」。
4. 出现的每个数字（分数、样本量、参数）都能在材料里找到出处。
5. 结尾总结第一句是「本文中我们……」。
6. 文件保存在 `docs/<slug>.md`，文件名用传入的 slug 原样。
