# 《VibeKaggle》

> **副标题**：用大模型打 Kaggle 的全新人机协作方式
>
> **本书定位**：面向会一点 Python、未参加过 Kaggle 竞赛的读者。它不教你“亲手做完每一个步骤”，而是教你**设计并运行一条人机协作的竞赛工作流**：让自动化工具和 LLM Agent 承担可重复的执行与枚举，你把有限的时间花在验证设计、方向判断和工件审查上。
>
> **VibeKaggle 的工作定义（贯穿全书）** ：以**工件驱动**为物理基础，以**验证优先**为判断纪律，以**人定方向、Agent 执行**为分工原则，以**提交预算**为安全边界，在 LLM Agent 的吞吐能力之上，重新组织 Kaggle 竞赛的每一个环节。


## 前言：VibeKaggle 不是“用 AI 写代码”

Google 与 Kaggle 在 2026 年发布的《The New SDLC With Vibe Coding》给出了一个关键判断：随意提示和真正的工程之间，分水岭是**验证**。这份白皮书进一步提出了一个对全书具有组织意义的分解：**Agent = 模型 + Harness，比例大约是 10/90**。模型只占 10%，harness——指令、工具、MCP 服务器、沙箱、编排、护栏、可观测性——占 90%。大多数 Agent 失败，诚实地审视，是**配置失败**，不是模型能力失败。这意味着 VibeKaggle 的核心技能不是“写更好的提示”，而是**设计更好的 harness**：固定验证协议、规范工件命名、限制提交预算、约束工具集。

NVIDIA 的 4x Grandmaster 在 2026 年 3 月的 Kaggle Playground 竞赛中用 LLM Agent 夺冠，提供了一个 harness 设计的完整样本：超过 60 万行代码、850 个实验、从 850 个模型中选出 150 个做四级 stacking，全部在 human-in-the-loop 下完成。他的工作流中贯穿一条纪律：每个实验的 OOF 和测试预测都必须保存为可组合的工件文件。没有这条纪律，850 个实验只会制造不可复现的混乱，而不是一个可被 hill climbing 和 stacking 利用的解决方案空间。

与此同时，MLE-Bench 的数据给出了必要的清醒剂，但这个数据本身也在快速变化：o1-preview 驱动的 AIDE 基线奖牌率仅为 16.9%，而截至 2026 年中，MLEvolve 在完整 75 个任务上达到 65.3% 的奖牌率，且只用了标准时间预算的一半。这个演进本身就在讲述 VibeKaggle 的核心命题：Agent 的能力边界不是固定的，**harness 的质量决定了你能把这条边界推到多远**。而人不可让渡的角色，是在 Agent 的高吞吐量之上做**判断**——判断哪个方向值得深入、验证方案是否系统性偏差、工件是否可信、是否值得消耗一次提交。

这本书的组织方式因此与第一版根本不同：**工件规范不是附录，而是第 2 章的基础协议；自动基线不是可选项，而是每一个代表比赛章的第一个动作；Agent 协作不是策略章节的话题，而是贯穿全书的操作模板。**


## 第1章 VibeKaggle 的工作流全景：从第一天起就在协作中工作

> 第一版用一整章教“注册、提交、看排行榜”。第二版保留必要的基础操作，但把它们嵌入 VibeKaggle 的工作流框架中：**你不是先学会手动做完一切，再学怎么让 Agent 帮忙；你从第一个基线开始就在设计人机分工。**

**1.1 Kaggle 的五分钟导览**
比赛页面、数据页面、讨论区、排行榜、Notebooks 五大区域的位置与作用；区分“比赛”与“数据集”。【Mermaid：比赛页面导览图】

**1.2 选择一场“自动化友好”的入门比赛**
指标明确、有 `sample_submission`、讨论区有活跃的公开 notebook 可供 Agent 参考作为 scouting signal 而非复制来源。Agentic Kaggle Skill 的实践原则在这里落地：“Read Kaggle rules, data terms, metric, submission format, and scoring mode before modeling”。

**1.3 三份核心文件与提交格式**
`train.csv` / `test.csv` / `sample_submission.csv` 各自的内容与约束；Agent 生成提交文件时的**格式自检清单**（行数、列名、ID 顺序、缺失值、概率范围）。

**1.4 VibeKaggle 的第一个动作：建立工件目录，而不是先写模型**
在跑任何模型之前，创建 `artifacts/oof/`、`artifacts/test_preds/`、`artifacts/logs/`，确定命名规范：`train_oof_[MODEL]_[VERSION].npy` 和 `test_preds_[MODEL]_[VERSION].npy`。第一个基线——哪怕是一个常数预测——也必须产出合规的 OOF 和 test prediction 文件。理由：VibeKaggle 的每一次判断都依赖工件作为证据；没有工件，Agent 的高吞吐量只会制造混乱。【Mermaid：工件目录结构与数据流向图】

**1.5 三种提交路径及其安全边界**
手动网页上传 / Kaggle CLI / MCP 驱动的提交。核心原则：Agent 可以让提交“零摩擦”，但**零摩擦是风险不是优势**。提交预算和预览-确认机制是工作流的护栏，不是可选的附加功能。`safe-kaggle-mcp` 的设计在这里作为参照：不可逆操作默认经过 preview→commit 双调用确认，每日提交预算默认 5 次并在每次响应中向 Agent 呈现。【Mermaid：三种提交路径的安全层级对比图】

**1.6 排行榜解读**
Public LB 在 Agent 高频实验下噪声被放大，人必须更保守地对待提交决策；本地 CV 与 LB 的差异在 Agent 时代的解读方式。

**1.7 规则红线（精简版）**
外部数据、预训练模型、自动化行为的披露边界。

**1.8 小结**
本章结束时，读者应该拥有一个**带工件目录的空工作区**，以及一个已跑通的常数基线工件——而不是一份“我学会了手动提交”的笔记。


## 第2章 VibeKaggle 的操作系统：工件、验证、Agent、预算

> 这是全书最重要的章节。第一版把 MCP 和 Agent 放在“工具箱”位置，把工件规范放在附录。**第二版把它们倒过来：工件规范是地基，验证纪律是判断标准，Agent 和 AutoML 是建筑在这个地基上的执行层，提交预算是安全边界。**

**2.1 工件规范：VibeKaggle 的物理基础**
- 命名约定：`train_oof_[MODEL]_[VERSION].npy`、`test_preds_[MODEL]_[VERSION].npy`
- 目录结构：`artifacts/oof/`、`artifacts/test_preds/`、`artifacts/logs/`
- 每个工件必须附带的最小元数据：CV 分数、验证折索引、一行改动描述
- **为什么这是第 2 章而不是附录**：没有工件规范，“人看 OOF 做判断”是空话，“Agent 自动做 hill climbing”无从谈起，“验证污染”也无从检查。工件规范是 VibeKaggle 从叙事变为工作流的最小充分条件。【Mermaid：工件生命周期图——从基线到集成】

**2.2 验证优先：不可委托的判断纪律**
- Google 白皮书的判断在这里落地：验证方案的设计（折数、分层、分组、时间切分）必须由人完成，Agent 只负责执行
- **验证污染**：当 Agent 被允许“尝试多种 CV 方案并选最好的那个”时，验证本身就成了搜索空间的一部分。人必须**固定验证协议**，只允许 Agent 在固定协议下迭代模型和特征
- 操作原则：Agent 的任何“随机划分”建议在时序数据中应被默认拒绝；Agent 生成的任何特征在使用前必须通过人设计的泄漏检查
- Agentic Kaggle Skill 的实践表述：“Build metric-correct baselines with stable folds and out-of-fold predictions”。【Mermaid：验证污染的形成机制图】

**2.3 LLM Agent 的能力边界：执行和枚举，而非判断**
- MLE-Bench 的演进数据：基线 16.9% → 先进 harness 下 65.3%。边界不是固定的，但**边界的位置取决于 harness 设计，而非模型选型**
- Agent 擅长的：EDA 代码生成、baseline pipeline 编写、批量特征变换实验、超参数扫描、实验结果汇总、stacking 组合的**候选生成**
- Agent 不擅长的：判断哪个方向值得深入、识别验证方案中的系统性偏差、在语义层面判断特征是否合理、决定是否提交
- 操作含义：人向 Agent 发出的指令应该是**带约束的请求**——“train a kfold XGBoost model. Save the OOF and the Test PREDS to disk as Numpy files”——而不是“帮我建个模型”。NVIDIA 冠军工作流的指导方式正是这种约束式指令。【Mermaid：Agent 能力边界与人的判断层叠图】

**2.4 AutoML 与表格基础模型：强基线的快速来源**
- AutoGluon 的多层 stacking 能力：在原始数据上 4 小时训练即可在部分 Kaggle 竞赛中击败 99% 的参赛者。AutoGluon 1.5 extreme 等后续版本在 Elo 基准上继续提升。
- TabPFN 等表格基础模型在中小规模数据上提供零调参的替代基线
- 正确用法：AutoML/基础模型产出**第一个有 CV 分数的合规工件**，人据此判断“当前数据上不费力能做到多好”，再决定人工投入的方向
- 边界：AutoGluon 的默认处理不总是最优；人工语义填充和领域特征是否带来增量，必须用同一 CV 协议下的工件对比来回答。【Mermaid：AutoML 基线在竞赛决策中的位置图】

**2.5 MCP：让 Agent 持续操作平台，安全是内置的**
- MCP 的核心价值：让下载→EDA→训练→工件落盘→提交预演成为 Agent 可持续运行的一条流水线，而不是在网页、CLI、Notebook 之间手动切换
- `safe-kaggle-mcp` 的具体安全机制作为教学案例：preview→commit 确认令牌（submit/delete/publish）、每日提交预算默认 5 次并在每次响应中向 Agent 呈现、`<untrusted-content>` 围栏防止提示注入、凭证不进入模型上下文
- 一个端到端 MCP 工作流示例：从“帮我看看这个比赛现在什么情况”到“跑一个 baseline，保存工件，但只允许提交 1 次”。【Mermaid：MCP 驱动的端到端流水线图】

**2.6 本章的验收任务**
- 在同一个表格数据集上，用 AutoGluon 跑出一个合规基线工件
- 用 LLM Agent 生成一版 EDA 代码并执行，人工标注其中哪些结论是数据支持的、哪些需要核实
- 配置一次 MCP 提交预演（dry-run），确认预算和确认机制生效

- Agent 可以执行 CV，但**验证方案的设计和泄漏检查是人不可让渡的职责**
- 检查 Agent 生成的特征是否无意中包含了只在预测时刻才能知道的信息。【Python 代码示例：固定 CV 协议 + 泄漏检查清单】

- 用 OOF 工件做 hill climbing 和 meta-model stacking 的基本流程

## 第20章 验证与评估：Vibe 时代更不可让渡的判断

> 当 Agent 能以 10 倍速度生成实验时，**验证方案的质量直接决定了这些实验是在帮你还是在骗你**。Google 白皮书的核心判断在这一章成为全书的方法论收束：验证不是建模之后的检查步骤，而是**决定哪些实验值得做的前提**。本章是整个 VibeKaggle 工作流的“刹车系统”。

**20.1 指标选择的不可委托性**
RMSE/MAE/RMSPE、准确率/AUC/LogLoss 的选择是人的判断，不是 Agent 的搜索空间。每个指标隐含的“什么是好”的价值观，必须由人根据竞赛的业务背景和数据性质来定。【Python 代码示例：sklearn 多指标计算 + 选择理由记录】【Mermaid：指标选择决策树】

**20.2 交叉验证方案的设计：Agent 执行，人设计并审核**
折数、分层、分组、时间切分的方案由人设计；Agent 执行并产出工件，人检查工件中的验证折索引是否符合设计。【Python 代码示例：固定 CV 协议 + 工件折索引审计】【Mermaid：CV 方案设计与审计流程图】

**20.3 验证污染：Agent 时代最隐蔽的过拟合**
当 Agent 被允许尝试多种 CV 方案并选最好的那个，验证本身就成了被优化的对象。人必须**固定验证协议**，只允许 Agent 在固定协议下迭代模型和特征。NVIDIA 冠军工作流中 850 个实验之所以可解释，正是因为验证协议在整个过程中保持固定，工件使事后审计成为可能。【Python 代码示例：验证协议锁定 + Agent 实验日志审计】【Mermaid：验证污染的形成与阻断图】

**20.4 目标泄漏检查清单（升级版）**
在传统泄漏检查项之外，增加：“Agent 生成的特征是否无意中包含未来信息”和“工件的验证折索引是否符合时间/分组约束”。Agentic Kaggle Skill 的实践原则 “Build metric-correct baselines with stable folds and out-of-fold predictions” 在这里转化为可操作的自查清单。【Python 代码示例：泄漏自查清单的代码化检查】

**20.5 本地 CV 与 LB 差异在 Agent 高频提交下的解读**
LB 信号的噪声被 Agent 的高提交频率放大；人必须更保守地对待提交决策。提交预算本身就是一种强制纪律：`safe-kaggle-mcp` 默认每日 5 次的预算迫使 Agent 不能在 LB 上做穷举搜索。【Mermaid：本地 CV、LB 与提交预算的关系图】

**20.6 小结：验证是 VibeKaggle 的第一性纪律，不是建模的附属品**


## 第21章 调优与集成：Agent 搜索，人选择

**21.1 超参数搜索 largely 委托给 Agent/AutoML**
人设定搜索空间和计算预算；Agent 执行并产出工件。搜索本身不是判断，**搜索空间的边界**才是判断。【Python 代码示例：预算约束下的 Agent 超参数扫描】

**21.2 集成的“选择”不是搜索问题**
哪些模型进入集成、用什么 meta-learner、权重是否稳定，需要人查看 OOF 工件的质量和相关性结构。NVIDIA 的冠军方案从 850 个模型中选出 150 个做四级 stacking，**选择过程**包含人对 OOF 质量、模型多样性和集成复杂度的判断，而不是纯粹的自动 hill climbing。【Python 代码示例：OOF 相关性矩阵 + 集成候选的人工筛选记录】【Mermaid：集成选择的人机分工图】

**21.3 AutoGluon 的多层 stacking vs 人工定制的 stacking**
AutoGluon 的 stacking 是自动化的强基线；人工 stack 的价值在于引入 AutoGluon 之外的模型家族（NN、不同预处理下的 GBDT、基础模型工件）。人判断何时人工 stack 的边际收益不再值得复杂度代价。【Python 代码示例：AutoGluon 集成工件 + 外部模型工件的混合 stacking】

**21.4 Agent 驱动的集成实验管理**
工件规范让 Agent 可以自动做 hill climbing 的候选生成；**人审核最终集成的 CV 稳定性和复杂度代价**，并控制提交。KDD Cup 2026 的 NVIDIA 方案中，“make every attempt inspectable” 的原则在这里同样适用：执行轨迹和工件使集成的每一步可审计。【Python 代码示例：Agent 生成集成候选 + 人工审核稳定性指标】

## 第22章 VibeKaggle 的策略与心态

**22.1 选择比赛的标准**
增加“自动化工具在该模态上的成熟度”维度：表格比赛的 Agent 杠杆最高（AutoGluon + 工件管理的组合已经过验证），图像/时序的杠杆较低但仍在快速演进。MLE-Bench 的数据可以帮助读者建立对“当前 Agent 能在什么类型的任务上做到什么程度”的现实认知。【Mermaid：比赛选择的多维度决策图】

**22.2 先让 Agent 跑自动基线，但不要在第一小时就提交**
先看 CV 和工件质量，再决定是否消耗提交预算。NVIDIA 的冠军工作流中，850 个实验在 GPU 加速下快速执行，但提交决策始终是审慎的、基于工件证据的。

**22.3 提交预算作为工作流的内置约束**
Agent 让提交“零摩擦”，但零摩擦是风险。人必须保留**提交决策权和预算控制权**；`safe-kaggle-mcp` 的默认 5 次/日预算和 preview→commit 机制是合理的起点。Google 白皮书的 10/90 分解在这里得到具体体现：提交安全不是模型能力问题，而是 harness 设计问题。

**22.4 团队协作的新形态：人类队友 + Agent 队友**
人负责方向和验证，Agent 负责实验吞吐和工件生产。KDD Cup 2026 的 NVIDIA 团队用“constrained harness around a small, fixed LLM”获得第二名，说明**harness 设计的质量比模型规模更能决定 Agent 协作的上限**。

**22.5 从“我会做 Kaggle”到“我会指挥系统做 Kaggle”**
竞赛履历的价值正在从手工能力转向**工作流设计能力和判断质量**。Google 白皮书的谱系框架——从 vibe coding（随意提示、最小验证）到 agentic engineering（形式化规格、自动化评估、生产系统）——为读者提供了一个自我定位的坐标：你在这条谱系上移动的距离，由验证的严谨度决定，而不是由使用哪个模型决定。
